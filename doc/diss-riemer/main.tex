\section{Block Based Programming}
\label{sec:block-based-programming}

Visual code editors that make use of drag and drop are commonly referred to as \enquote{block based} editors or programming languages. The probably most prominent example in the space is Scratch, which was released in 2007 \cite{maloneyScratchProgrammingLanguage2010} and implements its own programming language. Today Scratch is available as a browser application \footnote{\url{https://scratch.mit.edu/}} and the block editor user interface is built upon Googles Blockly library\footnote{\url{https://developers.google.com/blockly}}.

Scratch has demonstrated that visual programming environments are an excellent way for learners to take first steps in programming. It introduces a metaphor of \enquote{actors} acting out on a \enquote{stage} to describe a canvas on which objects can be moved around. Code is structured in terms of these actors and stages and can change their (often visual) properties. The concept of stacking and nesting blocks enforces proper indentation of code without the possibility of creating any syntactical errors. Having a sidebar to see available tools lowers the requirement to remember available options. It also adds the possibility to explore what options are provided by Scratch.

One common problem with Scratch is that its very carefully designed approach to increase accessibility resulted in deviations from programming languages used in the industry. Apart from the obvious fact that Scratch uses visual programming, the semantics of the underlying language are not always compatible with common languages like C, Java or Python.

Event based programming

Concurrent by default

Organisation of code in actors, not files

Of course C, Java and Python are all capable of event based programming. Common user interfaces libraries like Qt or JavaFX also hide the existance of a main loop inside their own code. So compared to Scratch these are more advanced concepts in real world programming languages and therefore not common entry points when learning how to program.

One common step after Scratch is the MIT App Inventor. It keeps the idea of block based programming but changes the metaphor from some kind of \enquote{stage play} to ultimately more conventional app development. This includes the availability of common user interface elements like buttons, checkboxes, labels, list views, text boxes, ...

\chapter{Blattwerkzeug: Grammar-based descriptions of block based development environments}

This chapter describes a formal definition that can be used to generate block based subsets of existing programming languages as well as \enquote{artificial} languages with a custom runtime. We call this formal definition a grammar, because the mental model of modelling a language in Blatt\-Werkzeug is very similar to constructing a formal grammar in compiler construction. But the purpose of the BlattWerkzeug grammar is sort of inverse to those of grammars in compiler construction: Instead of aiding in the conversion from a raw string to an abstract syntax tree, the BlattWerkzeug grammar is used to validate existing abstract syntax trees and to convert these trees into a properly formatted string representation of the corresponding program.

The previous paragraph mentioned \enquote{subsets of existing programming languages}. This is not a technical limitation: The grammar is capable of expressing real world programming languages in their entirety, as long as they are expressible in a context free grammar. But the resulting editors would be very tedious to use. This might or might not be a solvable problem, but no matter what it is simply out of scope for this endeavour. So there is no hard limit like along the lines of \enquote{the tooling rejects grammars after defining X types}.

\section{Syntax of Data Type Definitions}

Ultimately all data structures described in this document (abstract syntax trees, grammars, block languages) will be stored in the form of a JSON document at some point. All formal data type definitions therefore take the form of TypeScript type specifications and are taken from the BlattWerkzeug source code. They are not verbatim copies, but slightly compacted to improve readability. For example the codebase follows the convention of using a \texttt{Description}-suffix to denote types which are data-only. This helpful to distinguish the domain of types when moving through the source code while programming, but redundant when explaining.

\section{Blattwerkzeug Abstract Syntax Trees}
\label{sec:blattwerkzeug-ast}

The intended semantics of nodes in BlattWerkzeugs abstract syntax tree are always identifiable via a typename that consists of a language name and a local type name. Optionally a node stores atomic data as strings called \enquote{properties} and children in so called \enquote{named child groups}. A tree may be valid in the context of a specific grammar (see \cref{sec:grammar-specification}), but the tree itself has no concept of validity beyond the TypeScript type definition and in extension the JSON specifications when parsing a tree from it's string representation. The same goes for the visual representation: The tree itself requires a block language (see \cref{sec:block-language-specification}) in order to have a mapping to elements of a user interface. The formal data type definition is in \cref{lst:type-node-description}. \Cref{lst:example-grammar-html-typedef-content-model} shows an example grammar that introduces two \texttt{typedef}s: \texttt{metadata-content} which is meant to be used in \texttt{head} and \texttt{flow-content} which is meant to be used in \texttt{body}.



\begin{listing}[H]
\begin{minted}{typescript}
interface NodeDescription {
  name: string
  language: string

  properties?: Record<string, string>
  children?: Record<string, NodeDescription[]>
}
\end{minted}
\caption{Abstract syntax tree datatype}
\label{lst:type-node-description}
\end{listing}

The structure itself and the intentions for properties and named child groups are best understood by example. \Cref{ast:name-only} shows a minimal example of a tree containing nothing but a node of type \texttt{ruby.null}. Having the \texttt{language} as a namespace ensures that commonly used constructs like \texttt{if}, \texttt{class}, \texttt{expr}, ... do not clash when using different languages in a single tree. The \texttt{name} itself can be chosen arbitrarily, but should reflect the syntax element that is being represented. In the graphical representation nodes are depicted as boxes with the typename as the title of the box in \mintinline{ruby}{"${language}.${name}"} notation.

\section{Boolean Expression Language Example}
\label{sec:boolean-expression-language-example}

This section implements a possible syntax for basic language to denote boolean expressions by providing a grammar.

As with the AST, the canonical representation of grammars would be a JSON-document. There is however a visualisation called \enquote{Meta Grammar}, which is used as part of the block editor and also lends itself to be represented in text. The formal specification will be given in \Cref{sec:grammar-specification}, the following examples focus on the concepts of the meta grammar definition.

This example language demonstrates the basic concepts for structural validation of the BlattWerkzeug grammar. In text form, an example of a valid expressions for this proposed syntax would be $\neg(A \land false) \lor (\neg B \land true)$. This example includes the boolean values $true$ and $false$, variables $A$ and $B$, the unary operation of a negation and the binary operation for the logical AND and OR.

In the abstract syntax tree, we want to represent the atomic values $true$ and $false$ as two distinct types of nodes. \Cref{lst:bool-grammar-true-false} shows the meta grammar representation for this use case. It defines the node types \texttt{bool.true} and \texttt{bool.false}. Therefore trees consisting of exactly these node types as a root could be validated by the grammar\footnote{Technically the meta grammar representation uses the first defined type as root, so in strict terms only a tree consisting of \texttt{bool.true} would validate.}.

\begin{listing}[H]
\begin{minted}{text}
grammar bool {
  node true  { }
  node false { }
}
\end{minted}
\caption{Boolean Expression Grammar: constants $true$ and $false$}
\label{lst:bool-grammar-true-false}
\end{listing}

To introduce free variables, a node called \texttt{var} is introduced in \cref{lst:bool-grammar-var}. Different variables are distinguished by the property (\texttt{prop}) called \texttt{name} and for the moment any \texttt{string} (this includes unwanted characters such as newlines) is a valid identifier.

\begin{listing}[H]
\begin{minted}[highlightlines={4-6}]{text}
grammar bool {
  node true  { }
  node false { }
  node var {
    prop name string
  }
}
\end{minted}
\caption{Boolean Expression Grammar: User defined variables }
\label{lst:bool-grammar-var}
\end{listing}

So far successfully validated \enquote{trees} could only ever consisted of a root node. In order to support negation, another new node \texttt{neg} is introduced in \cref{lst:bool-grammar-neg-explicit}. This introduces a child group named \enquote{value} using the \texttt{children} specifier. The right hand side of the \texttt{::=} delimiter is in the style of the extended Backus-Naur form (EBNF). So in this specific example there may be a single child that is either of node type \texttt{true}, \texttt{false}, \texttt{var} or \texttt{neg}.

\begin{listing}[H]
\begin{minted}[highlightlines={7-9}]{text}
grammar bool {
  node true  { }
  node false { }
  node var {
    prop name string
  }
  node neg {
    children value ::= true | false | var | neg
  }
}
\end{minted}
\caption{Boolean Expression Grammar: Negation }
\label{lst:bool-grammar-neg-explicit}
\end{listing}

As the grammar in \cref{lst:bool-grammar-neg-explicit} is the first one to allow children in trees, we can take a look at \cref{fig:boolean-expr-examples-neg} for examples of valid and invalid trees. The valid trees show the structure of things that can be represented right now, essentially chains of negations that end in \texttt{true}, \texttt{false} or a \texttt{var}. The invalid example \cref{fig:boolean-expr-examples-neg-invalid} will however result in the following errors:

\begin{enumerate}
\item Root: Unexpected child group \enquote{value}
\item Root: Missing property \enquote{name}
\end{enumerate}

In practice these kinds of errors about structurally invalid trees are not expected to be very common: Transformations take place using specialised drag \& drop tools with pre-defined blocks that are available. But when changing a grammar after having created some trees according to the previous version of the grammar, such errors are part of the typical development process.

\subsection{Terminal Symbols}

We can take the two valid examples one step further and take a look on how they would be rendered in text form:

\begin{enumerate}
\item \Cref{fig:boolean-expr-examples-neg-var} renders to $A$, but should be $\neg A$
\item \Cref{fig:boolean-expr-examples-neg-double-false} renders to an empty string, but should be $\neg \neg false$
\end{enumerate}

This incorrect result is due to missing information in the grammar, the trees itself are fine. So far the only aspect that was represented in the rendered output was the value of the \texttt{prop name} of \texttt{var} and the observation, that this \texttt{prop} was stored as a child node of the root \texttt{neg} node. This is because in addition to defining the structure of the data, the defined \texttt{node}s also contain instructions on how to visually represent them. But \cref{lst:bool-grammar-neg-explicit} does not define any instructions on how to represent the \texttt{true} and \texttt{false} nodes.  We therefore extend the grammar in \cref{lst:bool-grammar-neg-explicit-terminals} to include \textit{terminal symbols}. Now the instructions for the \texttt{true} and \texttt{false} node convey the corresponding terminal symbols that should be used for the string representation. The unicode negation character \texttt{¬} is used for the \texttt{neg} node and demonstrates that the order of instructions is important: During text rendering the instructions in a node will be followed from top to bottom. These examples also demonstrate that \texttt{children} instructions do not have a representation of their own (unlike \texttt{prop}), but they do instruct the rendering process to recurse into the nodes in that named child group. After extending the grammar with the terminal symbols for \texttt{true}, \texttt{false} and \texttt{neg}, their text representation matches the expected representation exactly.

\begin{listing}[H]
\begin{minted}[highlightlines={2,3,8}]{text}
grammar bool {
  node true  { "true" }
  node false { "false" }
  node var {
    prop name string
  }
  node neg {
    "¬"
    children value ::= true | false | var | neg
  }
}
\end{minted}
\caption{Boolean Expression Grammar: Negation with terminal symbols}
\label{lst:bool-grammar-neg-explicit-terminals}
\end{listing}

\subsection{Visualisation issues when avoiding redundancy}
\label{sec:bool-grammar-visualise-redundancy}

Building upon these principles \cref{lst:bool-grammar-exp-bin-redundant} introduces the binary expression \texttt{bin} with childgroups for \texttt{left} and \texttt{right}. This serves as another example on how the order of instructions inside a node are used during the rendering transformation: When rendered the \texttt{op} will visually separate the the \texttt{left} child from the \textrm{right} child.

\Cref{lst:bool-grammar-exp-bin-redundant} on line 13 also showcases the \texttt{enum} restriction for properties: Instead of allowing any string value to be used as an \texttt{op}eration, the only permitted values are defined as the \enquote{and} and \enquote{or} operations in their respective mathematical notation.

An unpleasant aspect of \cref{lst:bool-grammar-exp-bin-redundant} is the excessive redundancy regarding the \texttt{children} types: \texttt{left} and \textrm{right} both state \texttt{true | false | var | neg | bin} and the \texttt{value} of \texttt{neg} had to be updated to include \texttt{bin}. All of these occurences must be kept identical, as they represent the concept of \enquote{being able to use any expression here} that applies to all child groups in this example.

\begin{listing}[H]
\begin{minted}[escapeinside=§§,highlightlines={9,11-15}]{text}
grammar bool {
  node true  { "true" }
  node false { "false" }
  node var {
    prop name string
  }
  node neg {
    "¬"
    children value ::= true | false | var | neg | bin
  }
  node bin {
    children left  ::= true | false | var | neg | bin
    prop op  string { enum "§$\land$§" "§$\lor$§" }
    children right ::= true | false | var | neg | bin
  }
}
\end{minted}
\caption{Boolean Expression Grammar: Unary and Binary expressions with redundancy}
\label{lst:bool-grammar-exp-bin-redundant}
\end{listing}

In conventional grammars this can be solved by introducing a new nonterminal symbol which contains productions that may result in exactly the nonterminals which we expect in the place of an expression. In Blatt\-Werkzeug we can emulate this behaviour using a node with a single child, as demonstrated in \cref{lst:bool-grammar-exp-bin-avoid-redundancy-node}. Semantically this works fine, but for people working with the block editor it introduces an unwanted side effect: The \texttt{exp} block has no visualisation. For the text-only representation this is helpful: If the examples in \Cref{fig:boolean-expr-examples-neg} would be rendered using \cref{lst:bool-grammar-exp-bin-avoid-redundancy-node}, the results would be exactly as before.

\begin{listing}[H]
\begin{minted}[escapeinside=§§,highlightlines={9,12,14,16-18}]{text}
grammar bool {
  node true  { "true" }
  node false { "false" }
  node var {
    prop name string
  }
  node neg {
    "¬"
    children value ::= exp
  }
  node bin {
    children left  ::= exp
    prop op  string { enum "§$\land$§" "§$\lor$§" }
    children right ::= exp
  }
  node exp {
    children exp   ::= true | false | var | neg | bin
  }
}
\end{minted}
\caption{Boolean Expression Grammar: Unary and Binary expressions with node to avoid redundancy}
\label{lst:bool-grammar-exp-bin-avoid-redundancy-node}
\end{listing}

\subsection{Designing truth values}

Modelling \texttt{true} and \texttt{false} as distinct nodes closely resembles their nature as classical keywords in grammars for conventional programming languages. Any object oriented programming language will most introduce the terminal symbol \texttt{class} in the respective grammar and in extension this idea of \enquote{surely these must be keywords} seems like a natural fit to the \texttt{boolean} datatype.

But as BlattWerkzeug already implements data types for the \texttt{prop} values of nodes, there is also a \texttt{bool} type. An alternative way to model the \texttt{true} and \texttt{false} values would therefore be as shown in the following

\begin{listing}[H]
\begin{minted}[escapeinside=§§,highlightlines={2-4, 6}]{text}
grammar bool {
  node value {
    prop value bool
  }

  typedef expr ::= value | var | neg | bin

  // Rest of grammar as seen before
}
\end{minted}
\caption{Boolean Expression Grammar: Single node truth value}
\label{lst:bool-grammar-single-node-truth-value}
\end{listing}

\begin{wrapfigure}{r}{0.3\textwidth}
  \includegraphics[width=\linewidth]{screenshots/blocks-bool-checkbox}
  \caption{Visualisation of $(\neg A \lor true)$ with a checkbox}
  \label{fig:sidebar-sql}
\end{wrapfigure}

This representation removes any direct mention of the terminal symbols \texttt{true} and \texttt{false} from the grammar and replaces it with a semantically equivalent property. It does not change the expressiveness of the modeled language, but the way the user perceives it: \texttt{bool} properties are rendered as checkboxes. This drastically changes to complexity to deal with such values at runtime: A single click turns a \texttt{true} value into a \texttt{false} value.

\section{XML languages examples}
\label{sec:xml-languages-example}

Prior example focussed on ground rules for validation to define the structure of valid trees and barely touched the possibilities to control the representation of the text representation. This example will show how any XML language can be defined structurally at first, then extended to a valid XML-text-representation and at last refined to follow more conventional code layout by using indentation in the textual representation.

\subsection{Validation: sequence / allowed}
\label{sec:validation-sequence-allowed}

Our initial XML tree implementation will provide nothing but elements that may have elements or text as children. You can think of something along the lines of the simple \texttt{HTML} to be representable. Readers familiar with \texttt{HTML} will recognise many possibilities of things to validate: A single \texttt{<html>}-element as the root that contains at most one of each \texttt{<head>} and \texttt{<body>}, \texttt{<li>} that must be children of \texttt{<ul>} or \texttt{<ol>}, ... Many of these will be adressed in later sections, but for the moment we will postpone all these details of \texttt{HTML} to focus on the core tree structure of the document: Named elements that may contain any amount of text or children.

But there is a catch: \cref{lst:example-xml-structure-with-attributes} shows the final structure that can be represented at the end of this example. It require text nodes to be available before, between or after any number of \texttt{element} nodes. The semantics of \mintinline{text}{children "elements" ::= text* element*} would be \enquote{any number oft \texttt{text} followed by any number of \texttt{element}} and therefore forbid a \texttt{element} to appear in front of a \texttt{text}.

\begin{listing}[htb]
\begin{minted}[escapeinside=§§,highlightlines={5-9}]{text}
<p class="spaced">
  This is some HTML with attributes. And it has text ...
  <ul id="the-list">
    <li>
      ... that may be
      <mark>nested</mark>
      in
      <em>interesting</em>
      ways.
    </li>
  </ul>
</p>
\end{minted}
\caption{Example HTML: Some attributes, mixed text and elements}
\label{lst:example-xml-structure-with-attributes}
\end{listing}

\Cref{lst:xml-grammar-no-allowed-typedef} models around this by using a \texttt{typedef} to substitute both permitted values for a single reference in the \texttt{children} specification. As the \texttt{*}-cardinality is bound to the \texttt{typedef} and each instance of it may resolve to either \texttt{element} or \texttt{text} this changes the semantics in the desired way. In general this trick works if all substituted children share the same quantifier, no matter whether it was the implicit \texttt{1} or the explicit \texttt{?}, \texttt{+} and \texttt{*}.

\begin{listing}[H]
\begin{minted}[escapeinside=§§,highlightlines={5,10}]{text}
grammar xml {
  root = xml.element
  node element {
    prop "name" string
    children "elements" ::= child*
  }
  node text {
    prop "value" string
  }
  typedef child ::= element | text
}
\end{minted}
\caption{XML Grammar: Using \texttt{typedef} for order independent children}
\label{lst:xml-grammar-no-allowed-typedef}
\end{listing}

But mixing these cardinalities on children would need states like \texttt{child\_1\_seen} to be representable in the \texttt{node} definitions. In a normal grammar this would be a valid approach. But as we have already seen in \cref{sec:bool-grammar-visualise-redundancy} this approach falls flat when taking visualisation into account: The artificial \enquote{state} nodes would have no immediate visualisation and no meaning that could be conveyed for a typical user. Therefore BlattWerkzeug introduces the \texttt{allowed} specifier (\Cref{lst:xml-grammar-allowed}) for children that can be used in place of the implicit \texttt{sequence} modifier. When validating it checks the cardinality of the children without any respect for the order in which the child nodes appear in the syntax tree. This allows cardinalities to be mixed as required without resorting to some kind of encoding of state in the nodes themself.

\begin{listing}[H]
\begin{minted}[escapeinside=§§,highlightlines={5}]{text}
grammar xml {
  root = xml.element
  node element {
    prop "name" string
    children "elements" allowed ::= text* element*
  }
  node text {
    prop "value" string
  }
}
\end{minted}
\caption{XML Grammar: Explicitly \texttt{allowed} sequence}
\label{lst:xml-grammar-allowed}
\end{listing}

\Cref{lst:xml-grammar-structure} shows how to extend this grammar to support key-value-pairs as attributes. There is not much of a surprise going on in that listing: The \texttt{node} has properties for exactly \texttt{key} and \texttt{value}. With this addition the grammar is capable of expressing the structure of arbitrary \texttt{XML} documents, including the example \texttt{HTML} of \cref{lst:example-xml-structure-with-attributes}.

\begin{listing}[H]
\begin{minted}[escapeinside=§§,highlightlines={5,8-11}]{text}
grammar xml {
  root = xml.element
  node element {
    prop "name" string
    children "attributes"       ::= attribute*
    children "elements" allowed ::= text* element*

    prop "key"   string
    prop "value" string
  }

\subsection{XML terminal symbols and \texttt{visualises}}
\label{sec:possibility-separating-visualisation-from-structure}

The structural grammar from the previous chapter has no terminal symbols and will therefore render in a way that does not resemble \texttt{XML} at all, as it naturally misses all the pointy brackets for elements as well as the \texttt{key='value'} syntax for attributes. But even though the structure we have created so far is named \texttt{xml} in the grammar, it effectively describes quite a rather universal concept that could also be expressed in different syntactic ways like e.g. Slim\footnote{\url{https://slim-lang.com/}} or HAML\footnote{\url{https://haml.info/}}. We will use this possibility of different syntactic representations as an excuse to introduce visualisation grammars instead of directly coupling the structural information with syntactic information.

Key to this variable representation of syntaxtrees is the BlattWerkzeug concept of purely visual grammars. These visual grammars refer to another grammar that defines the structure. The visualising grammar is not permitted to make changes to that structure. This is achieved by having a sibling set of grammar directives which only provide means to provide information for the rendering algorithm. These directive may therefore only reference existing nodes, properties or children and can not specify their type. The coorespondence of structural and visual directives are as follows:

\begin{itemize}
  \item \texttt{node} → \texttt{visualize}
  \item \texttt{prop} → \texttt{interpolate}
  \item \texttt{children} → \texttt{each}
\end{itemize}

\Cref{lst:xml-visualisation-no-containers} shows how these directives can be combined with terminal symbols to represent a tree in XML syntax. Note that even a single grammar combining structure and syntax would have required use of the \texttt{interpolate} directive, as the \texttt{name} property of \texttt{element} needs to be repeated for the closing tag.

\begin{listing}[H]
\begin{minted}[escapeinside=§§]{text}
grammar xml visualises 3b919483-8a97-41a8-8798-a8bb386609ba {
  visualise element {
    "<"
    interpolate "name"
    each "attributes"
    ">"
    each "elements"
    "</"
    interpolate "name"
    ">"
  }
  visualise attribute{
    interpolate "name" space-before §\label{code:visual-xml.attribute.space-before}§
    "="
    interpolate "value" double-quote §\label{code:visual-xml.attribute.double-quote}§
  }
}
\end{minted}
\caption{XML Visualisation: \texttt{element} and \texttt{attribute}}
\label{lst:xml-visualisation-no-containers}
\end{listing}

The visualisation of \texttt{attribute} reveals two special rendering instructions: \texttt{space-before} (line \ref{code:visual-xml.attribute.space-before}) and \texttt{double-quote} (line \ref{code:visual-xml.attribute.double-quote}). These are called \textit{tags} in BlattWerkzeug and come in two categories: Some ``known tags'' help to deal with whitespace and common balanced characters such as quotes. In general tags may be used on any directive to aid the visualisation algorithms, but in this example both usages happen to appear on an \texttt{interpolate}. These specific tags can be used by the backends to add spaces and ''double quotes''.

\subsection{Visualisation with typical \texttt{XML} formatting}
\label{sec:visualisation-in-lines}

The visualisation presented in the previous section is sufficent to produce \texttt{XML} documents that are well formed on the syntactic level: Elements have the required opening and closing tags and attributes are key-value-pairs. But they are not exactly easy on the eyes: Everything is rendered in a single line, the convention of indenting children is not followed at all. Technically having everything in a single line works for a surprising number of programming languages: When following a C-Style syntax (Java, JavaScript, C++, Go, ...) there is often no syntactic requirement for linebreaks and sometimes not even for spaces. There are even tools for \enquote{Minification} that are used with scripting languages to shrink the filesize at the cost of readability.

But as a learning tool, BlattWerkzeug values readability. And Blattwerkzeug therefore provides means to influence the visualisation of the abstract syntax tree that helps to properly understand it. People using BlattWerkzeug for learning are not required to understand indentation rules or similar styling concepts. The grammar for the used programming language is expected to provide properly indented text out of the box.

This works by providing layout information in so called \texttt{container}s which come in two possible orientations: \texttt{vertical} and \texttt{horizontal}. The natural layout of BlattWerkzeug is to arrange everything horizontally, but \Cref{lst:xml-visual} demonstrates how \texttt{xml.element} uses a top level vertical container to change the default orientation in a way that puts every child in its own row. To keep the \texttt{<element key="value">}-output on a single line, this top level \texttt{vertical} container is followed immediately by a \texttt{horizontal} container. Otherwise the \texttt{"<"} and \texttt{">"} would be placed in their own line respectively. The same reasoning applies to the closing tag in the last nested \texttt{horizontal} container of \texttt{xml.element}.

\begin{listing}[H]
\begin{minted}[escapeinside=§§,highlightlines={3,4,10,13}]{text}
grammar xml visualises 3b919483-8a97-41a8-8798-a8bb386609ba{
  visualise element {
    container vertical {
      container horizontal {
        "<"
        interpolate "name" keyword
        each "attributes"
        ">"
      }
      container vertical indent {
        each "elements"
      }
      container horizontal {
        "</"
        interpolate "name" keyword
        ">"
      }
    }
  }
  visualise attribute{
    interpolate "name" space-before
    "="
    interpolate "value" double-quote
  }
}
\end{minted}
\caption{XML Visualisation: With containers for proper indentation and line breaks}
\label{lst:xml-visual}
\end{listing}

The elements in line 11 of \cref{lst:xml-visual} are also wrapped in a \texttt{horizontal} container that seems superfluous at first sight. But besides repeating the same orientation definition as its parent, it also adds the \texttt{indent} tag. This will add one level of indentation for all children rendered between \texttt{<element>} and \texttt{</element>} without the rendered children even knowing about this.

\section{Foundations of the generated editors}

Previous sections have shown examples of block editors that could be generated by a grammar. But it did not specify how exactly the visualisation works or what operations the resulting editors allow This section will give a brief overview on how this editor can be used, the components it is surrounded by and how \enquote{files} are represented in BlattWerkzeug.

\subsection{Visualisation algorithm}
\label{sec:visualisation-algorithm}

No matter whether a syntaxtree is visualised using the builtin BlattWerkzeug block editor, the blockly editor or pretty printed: The basic algorithm for visualisation is always following the same recursive model. The procedure is called with the root node. From there the tree is walked recursively according to the order of the attributes in the grammar.

\begin{enumerate}
  \item \label{vis:given}
    Given: A \texttt{node} and a \texttt{grammar}
  \item \label{vis:attributes}
    \texttt{node\_type} $\gets$ On \texttt{grammar}, look up the type of \texttt{node}
  \item For each \texttt{attribute} defined on the \texttt{node\_type}, in the order that was given when defining the grammar:
    \begin{enumerate}
      \item \label{vis:terminal}
        A terminal emits the symbol written in the grammar.
      \item \label{vis:property}
        A property, or an interpolation of a property, emits the value stored on the node.
      \item \label{vis:children}
        A child group takes the children of its category in stored order. Each child is passed to a recursive call of this procedure. That call walks the attribute list of the child's own type.
      \item \label{vis:container}
        A container stays on the current node and applies rules~\ref{vis:attributes}--\ref{vis:children} to the attributes listed inside it. A horizontal container lays those fragments in one row, a vertical container inserts a line break between successive fragments that produced text, and the tag \texttt{indent} indents the group.
    \end{enumerate}
\end{enumerate}

This high level description omits a few details which are discussed in later chapters:

\subsubsection{Example: $A \land (B \lor \neg true)$}

The boolean expression grammar defined in \Cref{lst:bool-grammar-exp-bin-redundant} was the more or less final example. It accepty binary expressions, unary expressions, constants and variables. The tree in \cref{fig:bool-a-and-b-or-not-true} is valid according to that specification. The following example demonstrates how the visualisation algorithm will turn this tree into the matching string representation. The walk starts at the root \texttt{bin}.

\begin{enumerate}
  \item Rule~\ref{vis:attributes} reads attributes \texttt{left}, \texttt{op} and \texttt{right}.
  \item Rule~\ref{vis:children}, applied to \texttt{left}, calls the procedure on the \texttt{var} child. Rule~\ref{vis:property} emits $A$.
  \item Rule~\ref{vis:property}, applied to \texttt{op}, emits $\land$.
  \item Rule~\ref{vis:children}, applied to \texttt{right}, calls the procedure on the inner \texttt{bin}:
    \begin{enumerate}
      \item Rule~\ref{vis:children}, applied to \texttt{left}, emits $B$.
      \item Rule~\ref{vis:property}, applied to \texttt{op}, emits $\lor$.
      \item Rule~\ref{vis:children}, applied to \texttt{right}, calls the procedure on \texttt{neg}:
        \begin{enumerate}
          \item Rule~\ref{vis:terminal} emits $\neg$.
          \item Rule~\ref{vis:children}, applied to \texttt{value}, calls the procedure on \texttt{true}. Rule~\ref{vis:terminal} emits \texttt{true}.
        \end{enumerate}
    \end{enumerate}
\end{enumerate}

\section{Grammar specification \& design}
\label{sec:grammar-specification}

The previous examples have demonstrated the grammars practical capabilities to visualise and validate common textual structures of programming languages. When devising this grammar (or even earlier: when deciding whether to devise a new grammar at all) the following principles emerged over time and guided what to include and what to cut:

\begin{description}
\item[Validate trees] \hfill\\
  This grammar is used to elegantly express ways to work with syntax trees in block based structures.
\item[Terminal symbols to represent syntax, not for parsing] \hfill\\
  Rendering a syntax tree should result in a valid text representation of the target language and this requires syntactic elements. Parsing a text and converting it to a BlattWerkzeug syntax tree is explicitly not considered to keep the grammar small.
\item[Augmenting real world programming languages] \hfill\\
  Most programming languages are described via a context free grammar and should therefore be expressable as a block language in BlattWerkzeug.
%\item[Rapid Prototyping] \hfill\\
%  Creating a block variation for a subset of existing programming language should be possible in a matter of minutes. The first creatable programs in a new grammar should be able to express expressions and basic output.
\item[Extensions for meaningful block based programming] \hfill\\
  A grammar that is validating and textually representing syntax trees accurately is a good baseline, but the goal is to make the resulting block languages easy to use as well.
\end{description}

This section serves as a complete overview of all grammar elements, provides a formal specification of the validation semantics and provides origination as well as reasoning for certain features. The visualisation aspects of grammars, such as terminal symbols, containers, ... are described in principal, but their visualisation semantics may slightly differ depending on the backend that is used for visualisation.

All sections will use slightly edited TypeScript data type definitions of the stored \texttt{JSON} representation as the basis for the specification. The actual definitions follow a naming schema where all serialized types hava a \texttt{Description} suffix and there are accompanying types for validation, serialization, pretty printing, ... As none of these implementation details are helpful to understand the core data structures they are left out.

Initial implementations of provided programming languages have been written directly as \texttt{JSON} documents. But later on the block based so called \textit{Meta-Grammar} as is described in \cref{sec:meta-grammar}. BlattWerkzeug is therefore sort of self hosting: It would be possible to describe its grammar in its own grammar specification language. The resulting output however would look like the textual representation of the meta grammar and there is no parser / interpreter to work with this representation.

\subsection{Root: \texttt{grammar} itself}

\begin{listing}[H]
\begin{minted}{typescript}

\end{minted}
\caption{Type definitions of BlattWerkzeug Grammar and accompanying core types}
\label{lst:grammar-and-core-types-description}
\end{listing}

\texttt{id} and \texttt{name} from lines 2 \& 3 are straightforward: They denote the internal primary key and the human readable way to convey what the grammar is about, this will typically be a programming language like Ruby, Elixir or Kotlin. Multiple grammars may have the same name. Or in other terms: There may be different implementations of the same programming language.

Following on lines 5 to 9 are basically four different buckets of type definitions: \texttt{types}, \texttt{foreign\-Types}, \texttt{visuali\-sations} and \texttt{foreignVisualisations}. Note that the \texttt{NodeType} definitions inside these are an unordered map and therefore there can't be any reliable precedence and also no duplication inside each bucket. This also explains why there are the \texttt{foreign} and unnamed \enquote{native} buckets: This distinction allows types in the grammar itself to override those that are imported (\enquote{foreign}). \Cref{sec:combining-grammars} explains the mechanisms and semantics that apply when grammars are combined. The distinction between \texttt{visualisation} and \texttt{type} is explained in \Cref{sec:visualising-grammars}, but essentially visualisations are a subset of types. Lines 11 \& 12 are ID references to other grammars that must be respected when either grammar is updated.

The \texttt{root} field on line 14 is only technically optional: It must be possible to save a grammar that has no root defined. In practice a grammar that does not define a root isn't very helpful. It could technically validate any given tree by trusting it to have a sensible root, but this opens a problem space so wide, that it is simply unfeasible. The field does not directly store any type information, but instead points to the type that must be used as root in the form of a \texttt{QualifiedTypename}. The root being optional has the minor inconvenience of adding the need for a \texttt{UNSPECIFIED\_ROOT} type of error that can occur during runtime and signals an error in the grammar instead of a problem with the given abstract syntax tree.

By convention the \texttt{name} of the grammar (like \texttt{XML}) will also be used for the node definitions of the defined languages. This is inteded to support workflows with embedded languages, the most common example would probably be \texttt{HTML} that may contain inline \texttt{JavaScript} and \texttt{CSS}. In practice this is intended do be done by combining grammars, but it is possible for a single grammar to define node type definitions for multiple languages.

Referencing a grammar nevertheless happens with both identifiers: A grammar may be referred to by using either a the technical name or a ID\footnote{Usually this will be a \texttt{UUID}, but for practical reasons this document will use more memorable IDs.}. In practice this can lead to like \texttt{xml} with ID 22 and \texttt{xml-0.9} with ID 13. This duality provides the flexibility to either reference an exact (and possibly immutable) specific grammar by ID or to reference a probably changing version by name.


The data structure and validation semantics are effectively a subset of \texttt{XML} schema\cite{W3CXMLSchema}: Every Blattwerkzeug abstract syntax tree could be expressed as an equivalent \texttt{XML} document. A BlattWerkzeug grammar could be transformed into an equivalent \texttt{XML} schema and both validations should produce a semantically equivalent result. Where applicable, this specification will therefore link to the corresponding specification the semantics are borrowed from.

The textual representation of the grammar semantics described in the following sections (which was used in the examples at \cref{sec:boolean-expression-language-example} and \cref{sec:xml-languages-example}) is loosely inspired by the RelaxNG compact notation \cite{clarkRELAXNGSpecification2001}. This notation and how it is a subset of the larger model is discussed in \cref{sec:meta-grammar}.

An implementation of explicit grouping for expressions as an attempt to allow cardinalities on these. \subsection{Influencing representation via \texttt{tags}}

The BlattWerkzeug grammar is intended to be as identical as possible over the various backends. All core concepts work the same, no matter whether the syntaxtree is represented using the builtin block editor, the Blockly editor or is rendered using the text representation. But at times there are concepts that are not applicable to all backends. Therefore there is an escape hatch to communicate free-form strings as additional instruction to the specific backends. As you have seen in the previous type definition listings, the \texttt{tags?: TagDescription[]} attribute is available on everything that is renderable. \texttt{TagDescription} is ultimately a \texttt{string} with a few optional type hints.

This consciously lax typing makes tags a good field for experimentation. Whitespace handling (see \Cref{sec:grammar-whitespace}) has been built on top of tags, is understood by all backends and could theoretically be pulled into another representation. The sections about the specific backends contain details about the tags they are supporting.

\subsection{Common requirement: controlling horizontal whitespace}
\label{sec:grammar-whitespace}

BlattWerkzeug started out by representing whitespace in the rendered output via literal whitespace terminal symbols \texttt{"~"} and \texttt{"\textbackslash n"}). Working with literal non-line-break whitespace characters is still supported today, the support for newline characters has been removed in favor of vertical containers (\cref{sec:grammar-container}). Instead of using literal whitespace in the grammar, it is preferable to communicate the need for whitespace via the following tags:

\begin{multicols}{2}
\begin{itemize}
\item \texttt{space-after}
\item \texttt{space-before}
\item \texttt{space-around}
\item \texttt{newline-after}
\item \texttt{newline-before}
\end{itemize}
\end{multicols}

When rendered, these tags expand to the corresponding whitespace or newlines with respect to the immediate sibling nodes: A \texttt{space-after} followed by a \texttt{space-before} is collapsed into a single space instead of two spaces. The \texttt{newline} tags are seldomly used directly, linebreaks are usually introduced by vertical containers.

The tags are attached to the attributes that emit text: terminals, properties, interpolated properties, and child groups (\texttt{sequence}, \texttt{allowed}, \texttt{parentheses}, \texttt{each}). A \texttt{between} separator is a terminal of its own and takes the same tags. Each of these attributes carries a single separator tag; \texttt{space-around} is the tag that requests a space on both edges. On a terminal, property, or interpolation the tag surrounds that value. On a child group it surrounds the group: \texttt{space-before} and \texttt{newline-before} meet the first rendered token, \texttt{space-after} and \texttt{newline-after} meet the last. A group that renders no tokens, for example an optional child that is absent, drops its tags along with its text, so the hole leaves no whitespace behind.

The same collapse happens wherever two edges meet while the tree is walked. Neighbouring attributes of one node merge, and so do a \texttt{between} separator and the child that follows it. A horizontal container keeps the leading whitespace of its first attribute and the trailing whitespace of its last attribute visible to whatever stands outside the container, so those edges merge as well. A vertical container inserts a linebreak between its children, and a facing \texttt{newline-before} or \texttt{newline-after} merges with that linebreak into a single line break. A space written as the symbol of a terminal stays part of that symbol. Whitespace that would sit at the very start or end of the generated text is discarded.

This mechanism was introduced to address issues when e.g. combining blocks that mix requirements for leading and trailing whitespace. \Cref{lst:grammar-explicit-whitespace-return} demonstrates how a \texttt{return}-like statement could be written to express \enquote{the \texttt{return} keyword is separated from the following expression using a space character} in both ways. The explicit space seems fine in the isolation of the \texttt{return}-node, but if we take a look at the \texttt{expr}-node this turns into a problem: That parenting node also ensures that there is a space character in front of every expression. When combined, this results in two spaces separating the \texttt{return} keyword from its expression. In this tiny example the error and the solution seem obvious: The \texttt{expr}-node should rely on its parent \texttt{return} node to define the whitespace.

\subsection{Mapping from context free grammars}
\label{sec:cfg-mapping}
To illustrate the strong correspondence of context free grammars and Blattwerkzeug grammars this section shows a formal mapping from a given context free grammar to a BlattWerkzeug grammar. It is important to keep in mind that these grammars serve different purposes: The context free grammar is used for parsing, the BlattWerkzeug grammar is used to prettyprint. What they have in common is the derivation tree of the context-free grammar, which is the abstract syntax tree when each production is already a construct worth editing\footnote{Or more practically speaking: A context free grammar that is strictly converted to a BlattWerkzeug grammar following these rules will be very unpleasant to use.}. When prettyprinting such a tree using the corresponding BlattWerkzeug grammar, the output may differ in syntactic details such as whitespace, but will stay semantically equivalent. In whitespace sensitive languages this requires the whitespace to be part of the formal grammar.

For a context-free grammar $G = (N, \Sigma, P, S)$ the grammar $B(G)$ is built in two phases. The setup in rules~\ref{map:sigma}, \ref{map:pi} and \ref{map:nu} is followed once. The emission rules~\ref{map:root}, \ref{map:typedef} and \ref{map:node} are then applied in sequence.

To keep this proof short, the examples below write $G$ in Backus-Naur form and the terminals in $\Sigma$ are the tokens of an input that has already been lexed: a keyword such as \texttt{const} is one fixed symbol, while an identifier or a number is one symbol whose spelling is carried along, rather than an explicit production over the characters \texttt{a}$\,\cdots\,$\texttt{z} or \texttt{0}$\,\cdots\,$\texttt{9}.

\begin{enumerate}[(a)]
  \item \label{map:sigma}
    Divide $\Sigma$ into the symbols that are emitted as terminal symbols and the symbols that are emitted as properties:
    $\Sigma = \Sigma_{\mathrm{terminal}} \cup \Sigma_{\mathrm{property}}$,
    with the two sets disjoint. A quoted symbol belongs to $\Sigma_{\mathrm{terminal}}$. A name that occurs on a right-hand side and has no explicit production of its own (effectively hidden by the lexer) belongs to $\Sigma_{\mathrm{property}}$.
  \item \label{map:nu}
    Let $\nu$ be a map from $\Sigma_{\mathrm{property}}$ to property names.
    For each token $t \in \Sigma_{\mathrm{property}}$, $\nu(t)$ is the name of the property that stores the spelling of an occurrence of $t$.
    Two tokens that occur in the same production receive different names.
  \item \label{map:pi}
    Let $\pi$ be an injective map from $P$ to type names whose image is disjoint from $N$.
    For each $A \in N$, enumerate $\{(A, \alpha) \in P\}$ as an indexed list
    $P_A = \bigl((A, \alpha_1), \ldots, (A, \alpha_k)\bigr)$.
    Position $i$ receives the type name $\pi(A, \alpha_i)$.
    Names from different positions, including positions in different lists, are distinct.
\end{enumerate}

With the setup in place, the following rules are used to emit $B(G)$.

\begin{enumerate}
  \item \label{map:root}
    The \texttt{root} of $B(G)$ is $S$.
\item \label{map:typedef}
  For each $A \in N$, emit
  \texttt{typedef A ::= $\pi(A, \alpha_1)$ | $\cdots$ | $\pi(A, \alpha_k)$}
  from the list $P_A$ of rule~\ref{map:pi}.
\item \label{map:node}
  For each position $(A, \alpha_i)$ of each list $P_A$, emit a \texttt{node} named $\pi(A, \alpha_i)$.
  Read $\alpha_i = X_1 \cdots X_n$ from left to right and emit one attribute per symbol, in that order:
  \begin{enumerate}
      \item \label{map:terminal}
        If $X_i \in \Sigma_{\mathrm{terminal}}$, emit the terminal symbol \texttt{"$X_i$"}.
      \item \label{map:property}
        If $X_i \in \Sigma_{\mathrm{property}}$, emit \texttt{prop} $\nu(X_i)$ \texttt{string}. The value of that property is the spelling of this occurrence of $X_i$, and $\nu$ assigns it a property name.
      \item \label{map:nonterminal}
        If $X_i \in N$, emit a \texttt{sequence} child group of cardinality 1 that references $X_i$. The compact notation leaves the cardinality implicit.
      \item \label{map:epsilon}
        If $\alpha = \varepsilon$, the node body is empty.
    \end{enumerate}
\end{enumerate}

  \item Rule~\ref{map:nu} assigns $\nu(\mathit{ident}) = \texttt{name}$ and $\nu(\mathit{number}) = \texttt{value}$.
  \item Rule~\ref{map:pi}, applied to \texttt{Decl}, builds the list

  \item Rule~\ref{map:typedef}, applied to $P_{\mathit{Decl}}$, emits \mintinline{text}{typedef Decl ::= decl}.
  \item Rule~\ref{map:node}, applied to the single position of $P_{\mathit{Decl}}$, opens \mintinline{text}{node decl}. Its right-hand side is read left to right:

      \item Rule~\ref{map:terminal}, applied to \texttt{"const"}, emits \mintinline{text}{"const"}.

      \item Rule~\ref{map:terminal}, applied to \texttt{";"}, emits \mintinline{text}{";"}.

  \item Rule~\ref{map:nu} assigns $\nu(\mathit{ident}) = \texttt{name}$ and $\nu(\mathit{number}) = \texttt{value}$.
  \item Rule~\ref{map:pi} builds the lists
    \begin{align*}
      P_{\mathit{Decl}} &= \bigl(
        (\mathit{Decl},\; \texttt{"let"}\,\mathit{ident}\,\mathit{OptInit}\,\texttt{";"}),\;
        (\mathit{Decl},\; \texttt{"const"}\,\mathit{ident}\,\texttt{"="}\,\mathit{number}\,\texttt{";"})
      \bigr), \\
      P_{\mathit{OptInit}} &= \bigl(
        (\mathit{OptInit},\; \texttt{"="}\,\mathit{number}),\;
        (\mathit{OptInit},\; \varepsilon)
      \bigr)
    \end{align*}
    and assigns the type names \texttt{decl\_let}, \texttt{decl\_const}, \texttt{opt\_eq} and \texttt{opt\_empty}.
  \item Rule~\ref{map:root}, applied to $S = \mathit{Decl}$, emits \mintinline{text}{root = Decl}.
  \item Rule~\ref{map:typedef}, applied to $P_{\mathit{Decl}}$, emits \mintinline{text}{typedef Decl ::= decl_let | decl_const}.
  \item Rule~\ref{map:typedef}, applied to $P_{\mathit{OptInit}}$, emits \mintinline{text}{typedef OptInit ::= opt_eq | opt_empty}.
  \item Rule~\ref{map:node}, applied to the first position of $P_{\mathit{Decl}}$, opens \mintinline{text}{node decl_let}. Its right-hand side is read left to right:
    \begin{enumerate}
      \item Rule~\ref{map:terminal}, applied to \texttt{"let"}, emits \mintinline{text}{"let"}.
      \item Rule~\ref{map:property}, applied to \texttt{ident}, emits \mintinline{text}{prop name string}.
      \item Rule~\ref{map:nonterminal}, applied to \texttt{OptInit}, emits \mintinline{text}{children init ::= OptInit}.
      \item Rule~\ref{map:terminal}, applied to \texttt{";"}, emits \mintinline{text}{";"}.
    \end{enumerate}
  \item Rule~\ref{map:node}, applied to the second position of $P_{\mathit{Decl}}$, opens \mintinline{text}{node decl_const}. Rules~\ref{map:terminal} and \ref{map:property} emit \mintinline{text}{"const"}, \mintinline{text}{prop name string}, \mintinline{text}{"="}, \mintinline{text}{prop value string} and \mintinline{text}{";"}.
  \item Rule~\ref{map:node}, applied to the first position of $P_{\mathit{OptInit}}$, opens \mintinline{text}{node opt_eq}. Rule~\ref{map:terminal} emits \mintinline{text}{"="} and rule~\ref{map:property} emits \mintinline{text}{prop value string}.
  \item Rule~\ref{map:node}, applied to the second position of $P_{\mathit{OptInit}}$, opens \mintinline{text}{node opt_empty}. Rule~\ref{map:epsilon} gives that node an empty body.
\end{enumerate}
\noindent
The emitted grammar is \cref{lst:cfg-mapping-decl-ext}. The program \texttt{let a;} uses \texttt{decl\_let} with an \texttt{opt\_empty} child. The program \texttt{let b = 3;} uses \texttt{decl\_let} with an \texttt{opt\_eq} child.

\section{Custom validation rules}

The presented grammar allows to define rules for immediate parent-child relationships and data types for properties. This is sufficent to describe the structure of many different documents, but can be cumbersome or outright impractical when describing relationships over more levels. BlattWerkzeug therefore also offers an API to define validators via custom TypeScript-code. This can't be done in the user-facing grammar-editor, but must be part of the compiled editor itself.

As the grammer is purpose built for the resulting editor, deciding on the scope of the grammar requires careful justification. As often in computer science, it would of course be possible to devise a grammar-system that could express arbitrary validation logic. And as the grammar borrows some inspiration of RelaxNG, there is precedence that could have been followed thoroughly (or RelaxNG could have been used directly).

Instead the grammar focussed on figuring out a small subset that can express the majority of programming language structures without leaving too many gaping validation holes. Over time, two main scenarios have occured again and again that defied general solutions. Under these circumstances the BlattWerkzeug grammar purposefully delegates to custom code solutions for validation:

\begin{enumerate}
\item Dependencies between nodes that introduce some kind of naming. The most common case are identifiers for variables and the like: Depending on the language they may have rules that include scoping, various typechecks, or the may be introduced outside the edited document. Seemingly more often than not a program can not be checked in isolation. The following list of examples is not complete, but gives an impression why not much energy was invested to describe a truly general solution to this problem space:

  \begin{itemize}
  \item Identifiers might be introduced by other syntaxtrees in the same project: Global variables, available functions, specified \texttt{CSS} classes, ...
  \item The correctness of an \texttt{SQL}-query is undecidable without knowing the schema of the database involved.
  \item Surrounding code including things like the Ssandard libraries for programming languages are change over time, a grammar may specify
  \item Depending on compiler configuration certain aspects of a language may be enable or prohibited.
  \end{itemize}

  All of these aspects are highly dependent on the specific programming languages beeing augmented. The general advice for BlattWerkzeug language creators is to model the grammar as strictly and close to a specific version (with possibly specific compiler instructions) as possible: Regarding the audience there does not seem to be much merit in making the grammar for e.g. \texttt{JavaScript} flexible enough to accomodate everything from version 1 (1997) to the version of 2026. Instead just pick the relevant features that are in focus of being teached and ensure them to be present. Or to phrase it in a positive way: Having multiple grammar variations for the same language is encouraged for didactic purposes.

  In some cases it seems promising to do some simple checks directly on the AST, \cref{sec:sql} does this to give immediate feedback about the correctness of a query in the light of a certain schema. But in general running the compiler or interpreter and providing its output to the user seems like a fallback that must be available.
\item The dependencies inside the tree are more complex than simple parent-child relationships. Examples for this include e.g. \texttt{HTML} that expects to have \texttt{<input>}-elements inside \texttt{<form>}-elements
\end{enumerate}

\Cref{sec:validate-html-rules-for-xml} shows an example how the rules for \texttt{HTML} could be expressed by the type system alone and then shows how custom validation rules are a preferable approach.

The BlattWerkzeug runtime defines a general validation API that takes an AST and a validation context that is the mutable validation state. \Cref{lst:typescript-specializedvalidator} shows the exact \texttt{class} that must be derived from. Earlier versions of the validator have been implemented using a simpler function interface that acted as a visitor being invoked, returning the validation issues it found on a certain node. But practical development showed that this approach came with major drawbacks:

\begin{enumerate}
\item Most validation requires building an extensive context: A certain node is only valid, if other nodes exist elsewhere in the tree. This would have to be rebuilt again and again when validation focusses on each node in isolation.
\item Having constructors available to formalize a two phase binding was very helpful: This way construction of validators can be as specific as the programming runtime requires it and the actual validation can then rely on that data.
\end{enumerate}

Grammar validation is also implemented using this API. In this case the constructor takes the \texttt{JSON}-grammar definition and creates an extensive map of available validators for all types that are defined. As hinted earlier, the grammar validator used to be some kind of special case that provided iteration over the syntaxtree and invoked validation functions.

In the current design the only thing that is special about the grammar validator is that it is guaranteed to run first. This ordering gives precedence to structural errors which are an indication for either incomplete or possibly malformed trees. Custom code validation is usually more concerned with semantic errors and depending on the context it may not be desireable to attempt to detect these on incomplete trees. By running later compared to the structural analysis, this kind of reaction is possible.

In general the validation code is very tightly coupled to the grammar.

Validation is one of the reasons why the quite simple structure of the AST is wrapped in a class: Having all sorts of query methods available felt like a good way to make them discoverable. \Cref{lst:sql-validator-table-names} gives a good impression how validation code looks like. It should make as little assumptions about the tree as possible, it therefore queries for any number of \texttt{sql.from} nodes. In practice this will most likely be either no node or one node, but the validation code then also works with queries that have multiple \texttt{FROM}, e.g. when they do sub-\texttt{SELECT}s.

The code does first gather all \texttt{FROM} nodes and searches this sub-tree for \texttt{sql.tableIntroduction} nodes. Limiting the search in this way is not strictly necessary, but in case of wildly malformed trees it attempts to not add semantic errors on nodes that are alredy marked as structural errors. Actually adding the error then checks the property \texttt{name} against the schema. Most validation code works in a similar fashion: It repeatedly uses \texttt{getNodesOfType(...)} to carve out sub-tree strucures and then calls \texttt{contex.addError(...)} in case some problem is detected.

Other common patterns include:

\begin{itemize}
\item Building sets of names known to be defined in certain sub-trees and checking identifiers against these, instead of checking against the context.
\item Doing basic checks on arguments for functions of the standard libraries.
\end{itemize}

\subsection{Example: HTML ancestry validation rules for XML}
\label{sec:validate-html-rules-for-xml}

For this example we will concentrate on common type of rule around ancestors found in HTML: The requirement that a certain element may only occur if there is a certain parent somewhere in the hierarchy. In HTML-terms this is called the \textit{content-model}: \enquote{A normative description of what content must be included as children and descendants of the element.} \cite[§3.2.5 Content models]{whatwgHTMLLivingStandard} The most obvious example is the distinction between permitted children in \texttt{<head>}- and \texttt{<body>}-elements: Everything in \texttt{<head>} is so called \textit{metadata-content}, everything in \texttt{<body>} is so called \textit{flow-content}. And inside the flow content there are (broadly speaking) markup elements intended to be used inside paragraphs: Think of elements like \texttt{<a>}, \texttt{<small>}, \texttt{<span>}, ... At a first glance, this distinction can be expressed nicely in the type system with three \texttt{typedef} declarations. \Cref{lst:example-grammar-html-typedef-content-model} follows this idea and shows a grammar that is capable of expressing the following basic \texttt{HTML} structures:

\begin{itemize}
\item \texttt{html}, has exactly two children in order:
  \begin{enumerate}
  \item \texttt{head}, specific occurences of \textit{metadata-content} in any order:
    \begin{itemize}
    \item Exactly one \texttt{title}
    \item Any number of \texttt{script}
    \end{itemize}
  \item \texttt{body}, any occurences of \textit{flow content} in any order:
    \begin{itemize}
    \item \texttt{h1}, \texttt{h2}, \texttt{h3}, \texttt{h4}, \texttt{h5}, \texttt{h6}, \texttt{p}, \texttt{div}, \texttt{a}
    \item \texttt{<div>} and \texttt{<a>} permit any \textit{flow-content}
    \item Everything except \texttt{<div>} permits any \textit{phrasing-content}, this refers to \texttt{<span>}, \texttt{<a>} and also includes text that is meant to be displayed
    \end{itemize}
  \end{enumerate}
\end{itemize}

\begin{listing}[p]
\begin{minted}{text}
grammar diss-html {
  root = html
  node html {
    children "document" sequence ::= head body
  }

  node title {
    prop "value" string
  }
  node script {
    prop "value" string
  }
  typedef metadata-content ::= title | script
  node head {
    children "children" allowed ::= title? script*
  }

  node hX {
    prop "level" integer
    children "children" allowed ::= phrasing-content*
  }
  node p {
    children "children" allowed ::= phrasing-content*
  }
  node span {
    children "children" allowed ::= phrasing-content*
  }
  node a {
    prop "href" string
    children "children" allowed ::= phrasing-content* | flow-content*
  }
  node text {
    prop "value" string
  }
  node div {
    children "children" allowed ::= flow-content*
  }
  typedef flow-content     ::= hX | p | div | a
  typedef phrasing-content ::= span | a | text
  node body {
    children "children" allowed ::= flow-content*
  }
}
\end{minted}
\caption{Minimal example for an HTML grammar using \texttt{typedef} for different content models}
\label{lst:example-grammar-html-typedef-content-model}
\end{listing}


After the structure of the resulting permitted documents is understood, we can now work through various shortcomings and interesting aspects of this approach from top to bottom.

The grammar is a structural grammar that does not define any terminal symbols. The visualisation can be externalised nicely in principle, but for this structure it will contain lots of repetetion as the fundamental HTML-syntax needs to be re-specified for every \texttt{node}.

The \texttt{HTML}-specification only allows a single \texttt{<title>}-element to be present in the \texttt{<head>}-element: \enquote{Zero or more elements of metadata content, of which no more than one is a title element and no more than one is a base element} \cite[§4.2.1 The head element]{whatwgHTMLLivingStandard}. The grammar itself is able to express this via the \texttt{?}-cardinality. But as the semantics of a \texttt{typedef} are a substitution, this can't express the required differences in cardinality. Instead the \texttt{children} definition of \texttt{head} resorts to \texttt{diss-html.title? diss-html.script*} to explicitly represent the mixed cardinalities.

The builtin BlattWerkzeug block editor does not immediately use grammars to visualize syntax trees, instead it relies on an intermediate structure called block language which adds a few more fine tuning options not present on the grammar level. These options concern representation matters: Details about colouring, the way the block structure should be made visible and the overall layout of the development environment.
