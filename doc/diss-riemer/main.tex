\section{Block Based Programming}
\label{sec:block-based-programming}

Visual code editors that make use of drag and drop are commonly referred to as \enquote{block based} editors or programming languages. The probably most prominent example in the space is Scratch, which was released in 2007 \cite{clark_relax_2001} and implements its own programming language. Today Scrtach is available as a browser application \footnote{\url{https://scratch.mit.edu/}} and the block editor user interface is built upon Googles Blockly library\footnote{\url{https://developers.google.com/blockly}}.

Scratch has demonstrated that visual programming environments are an excellent way for learners to take first steps in programming. It introduces a metaphor of \enquote{actors} acting out on a \enquote{stage} to describe a canvas on which objects can be moved around. Code is structured in terms of these actors and stages and can change their (often visual) properties. The concept of stacking and nesting blocks enforces proper indentation of code without the possibility of creating any syntactical errors. Having a sidebar to see available tools lowers the requirement to remember available options. It also adds the possibility to explore what options are provided by Scratch.

One common problem with Scratch is that its very carefully designed approach to increase accessibility resulted in deviations from programming languages used in the industry. Apart from the obvious fact that Scratch uses visual programming, the semantics of the underlying language are not always compatible with common languages like C, Java or Python.

Event based programming

Concurrent by default

Organisation of code in actors, not files

Of course C, Java and Python are all capable of event based programming. Common user interfaces libraries like Qt or JavaFX also hide the existance of a main loop inside their own code. So compared to Scratch these are more advanced concepts in real world programming languages and therefore not common entry points when learning how to program.

One common step after Scratch is the MIT App Inventor. It keeps the idea of block based programming but changes the metaphor from some kind of \enquote{stage play} to ultimately more conventional app development. This includes the availability of common user interface elements like buttons, checkboxes, labels, list views, text boxes, ...

\chapter{Blattwerkzeug: Grammar-Based Descriptions of Block Based IDEs}

This chapter describes a formal definition that can be used to generate block based subsets of existing programming languages as well as \enquote{artificial} languages with a custom runtime. We call this formal definition a grammar, because the mental model of modelling a language is very similar to constructing a context free grammar in compiler construction. But the purpose of the BlattWerkzeug-grammar is sort of inverse to those of grammars in compiler construction: Instead of aiding in the conversion from a raw string to an abstract syntax tree, the BlattWerkzeug grammar is used to validate existing abstract syntax trees and to convert these trees into a properly formatted string representation of the corresponding program.

Augmenting existing programming languages as a block based variation requires the specification of a grammar that ultimately emits valid source code of the target language.

\section{Syntax of Data Type Definitions}

Ultimately all data structures described in this document will be stored in the form of a JSON document at some point. This helpful to distinguish the domain of types when programming, but redundant when explaining.

\section{Blattwerkzeug Abstract Syntax Trees}

BlattWerkzeugs abstract syntax trees are identified via a typename that consists of a language name and a local type name. Optionally a node stores atomic data as strings called \enquote{properties} and children in so called \enquote{named child groups}. A tree may be valid in the context of a specific grammar (see \cref{sec:grammar-specification}), but the tree itself has no concept of validity beyond the TypeScript type definition and in extension the JSON specifications when parsing a tree from it's string representation. The same goes for the visual representation: The tree itself requires a block language (see \cref{sec:block-language-specification}) in order to have a mapping to elements of a user interface. The formal data type definition is in \cref{lst:type-node-description}.

\begin{listing}[!ht]
\begin{minted}{typescript}
interface NodeDescription {
  name: string
  language: string

  properties?: Record<string, string>
  children?: Record<string, NodeDescription[]>
}
\end{minted}
\caption{Abstract syntax tree datatype}
\label{lst:type-node-description}
\end{listing}

The structure itself and the intentions for properties and named child groups are best understood by example. \Cref{ast:name-only} shows a minimal example of a tree containing nothing but a node of type \texttt{ruby.null}. Having the \texttt{language} as a namespace ensures that commonly used constructs like \texttt{if}, \texttt{class}, \texttt{expr}, ... do not clash when using different languages in a single tree. The \texttt{name} itself can be chosen arbitrarily, but should reflect the syntax element that is being represented. In the graphical representation nodes are depicted as boxes with the typename as the title of the box in \mintinline{ruby}{"${language}.${name}"} notation.

\section{Boolean Expression Language Example}

This section implements a possible syntax for basic language to denote boolean expressions by providing a grammar.

As with the AST, the canonical representation of grammars would be a JSON-document. There is however a visualisation called \enquote{Meta Grammar}, which is used as part of the block editor and also lends itself to be represented in text. The formal specification will be given in \Cref{sec:grammar-specification}, the following examples focus on the concepts of the meta grammar definition.

This example language demonstrates the basic concepts for structural validation of the BlattWerkzeug grammar. In text form, an example of a valid expressions for this proposed syntax would be $\neg(A \land false) \lor (\neg B \land true)$. This example includes the boolean values $true$ and $false$, variables $A$ and $B$, the unary operation of a negation and the binary operation for the logical AND and OR.

In the abstract syntax tree, we want to represent the atomic values $true$ and $false$ as two distinct types of nodes. \Cref{lst:bool-grammar-true-false} shows the meta grammar representation for this use case. It defines the node types \texttt{bool.true} and \texttt{bool.false}. Therefore trees consisting of exactly these node types as a root could be validated by the grammar\footnote{Technically the meta grammar representation uses the first defined type as root, so in strict terms only a tree consisting of \texttt{bool.true} would validate.}.

\begin{listing}[!ht]
\begin{minted}{text}
grammar bool {
  node true  { }
  node false { }
}
\end{minted}
\caption{Boolean Expression Grammar: constants $true$ and $false$}
\label{lst:bool-grammar-true-false}
\end{listing}

To introduce free variables, a node called \texttt{var} is introduced in \cref{lst:bool-grammar-var}. Different variables are distinguished by the property (\texttt{prop}) called \texttt{name} and for the moment any \texttt{string} (this includes unwanted characters such as newlines) is a valid identifier.

\begin{listing}[!ht]
\begin{minted}[highlightlines={4-6}]{text}
grammar bool {
  node true  { }
  node false { }
  node var {
    prop name string
  }
}
\end{minted}
\caption{Boolean Expression Grammar: User defined variables }
\label{lst:bool-grammar-var}
\end{listing}

So far successfully validated \enquote{trees} could only ever consisted of a root node. In order to support negation, another new node \texttt{neg} is introduced in \cref{lst:bool-grammar-neg-explicit}. This introduces a child group named \enquote{value} using the \texttt{children} specifier. The right hand side of the \texttt{::=} delimiter is in the style of the extended Backus-Naur form (EBNF). So in this specific example there may be a single child that is either of node type \texttt{true}, \texttt{false}, \texttt{var} or \texttt{neg}.

\begin{listing}[!ht]
\begin{minted}[highlightlines={7-9}]{text}
grammar bool {
  node true  { }
  node false { }
  node var {
    prop name string
  }
  node neg {
    children value ::= true | false | var | neg
  }
}
\end{minted}
\caption{Boolean Expression Grammar: Negation }
\label{lst:bool-grammar-neg-explicit}
\end{listing}

As the grammar in \cref{lst:bool-grammar-neg-explicit} is the first one to allow children in trees, we can take a look at \cref{fig:boolean-expr-examples-neg} for examples of valid and invalid trees. The valid trees show the structure of things that can be represented right now, essentially chains of negations that end in \texttt{true}, \texttt{false} or a \texttt{var}. The invalid example \cref{fig:boolean-expr-examples-neg-invalid} will however result in the following errors:

\begin{enumerate}
\item Root: Unexpected child group \enquote{value}
\item Root: Missing property \enquote{name}
\end{enumerate}

In practice these kinds of errors about structurally invalid trees are not expected to be very common: Transformations take place using specialised drag \& drop tools with pre-defined blocks that are available. But when changing a grammar after having created some trees according to the previous version of the grammar, such errors are part of the typical development process.

We can take the two valid examples one step further and take a look on how they would be rendered in text form:

\begin{enumerate}
\item \Cref{fig:boolean-expr-examples-neg-var} renders to $A$, but should be $\neg A$
\item \Cref{fig:boolean-expr-examples-neg-double-false} renders to an empty string, but should be $\neg \neg false$
\end{enumerate}

This incorrect result is due to missing information in the grammar, the trees itself are fine. So far the only aspect that was represented in the rendered output was the value of the \texttt{prop name} of \texttt{var} and the observation, that this \texttt{prop} was stored as a child node of the root \texttt{neg} node. This is because in addition to defining the structure of the data, the defined \texttt{node}s also contain instructions on how to visually represent them. But \cref{lst:bool-grammar-neg-explicit} does not define any instructions on how to represent the \texttt{true} and \texttt{false} nodes.  We therefore extend the grammar in \cref{lst:bool-grammar-neg-explicit-terminals} to include \textbf{terminal symbols}. Now the instructions for the \texttt{true} and \texttt{false} node convey the corresponding terminal symbols that should be used for the string representation. The unicode negation character \texttt{¬} is used for the \texttt{neg} node and demonstrates that the order of instructions is important: During text rendering the instructions in a node will be followed from top to bottom. These examples also demonstrate that \texttt{children} instructions do not have a representation of their own (unlike \texttt{prop}), but they do instruct the rendering process to recurse into the nodes in that named child group. After extending the grammar with the terminal symbols for \texttt{true}, \texttt{false} and \texttt{neg}, their text representation matches the expected representation exactly.

\begin{listing}[!ht]
\begin{minted}[highlightlines={2,3,8}]{text}
grammar bool {
  node true  { "true" }
  node false { "false" }
  node var {
    prop name string
  }
  node neg {
    "¬"
    children value ::= true | false | var | neg
  }
}
\end{minted}
\caption{Boolean Expression Grammar: Negation with terminal symbols}
\label{lst:bool-grammar-neg-explicit-terminals}
\end{listing}

Building upon these principles \cref{lst:bool-grammar-exp-bin-redundant} introduces the binary expression \texttt{bin} with childgroups for \texttt{left} and \texttt{right}. This serves as another example on how the order of instructions inside a node are used during the rendering transformation: When rendered the \texttt{op} will visually separate the the \texttt{left} child from the \textrm{right} child.

\Cref{lst:bool-grammar-exp-bin-redundant} on line 13 also showcases the \texttt{enum} restriction for properties: Instead of allowing any string value to be used as an \texttt{op}eration, the only permitted values are defined as the \enquote{and} and \enquote{or} operations in their respective mathematical notation.

An unpleasant aspect of \cref{lst:bool-grammar-exp-bin-redundant} is the excessive redundancy regarding the \texttt{children} types: \texttt{left} and \textrm{right} both state \texttt{true | false | var | neg | bin} and the \texttt{value} of \texttt{neg} had to be updated to include \texttt{bin}. All of these occurences must be kept identical, as they represent the concept of \enquote{being able to use any expression here} that applies to all child groups in this example.

\begin{listing}[!ht]
\begin{minted}[escapeinside=§§,highlightlines={9,11-15}]{text}
grammar bool {
  node true  { "true" }
  node false { "false" }
  node var {
    prop name string
  }
  node neg {
    "¬"
    children value ::= true | false | var | neg | bin
  }
  node bin {
    children left  ::= true | false | var | neg | bin
    prop op  string { enum "§$\land$§" "§$\lor$§" }
    children right ::= true | false | var | neg | bin
  }
}
\end{minted}
\caption{Boolean Expression Grammar: Unary and Binary expressions with redundancy}
\label{lst:bool-grammar-exp-bin-redundant}
\end{listing}

\section{Grammar specification}
\label{sec:grammar-specification}

The previous examples have demonstrated the practical capabilities of the implemented grammar system. This section serves as a complete overview of all grammar elements and provides a formal specification of the validation semantics of the grammar. The visualisation aspects of grammars, such as terminal symbols, containers, ... are described in principal, but their visualisation semantics may slightly differ depending on the backend that is used for visualisation.

The validation semantics are a subset of XML schema. Where applicable, this specification will therefore link to the corresponding specification the semantics are borrowed from. The text representation of the grammar is loosely inspired by the RelaxNG compact notation \textcite{clark_relax_2001}.

The grammar itself is a collection of type definitions and a root specification. It may be referred to by using either a name or a UUID. As it is customary in tree structures, validation starts from the root, so the grammar needs to specify what that root is. This root specification comes in an indirect form, it denotes the fully qualified type name that must match the fully qualified typename of the root in the abstract syntax tree.

For practical purposes the \texttt{root} must be described as being optional: Grammars can be edited through either a text based or a drag \& drop editor in the BlattWerkzeug IDE itself and it would be very inconvenient if grammars without root specifications couldn't be saved due to a too strict type system. This has the minor inconvenience of adding the need for a \texttt{UNSPECIFIED\_ROOT} type of error that can occur during runtime and signals an error in the grammar instead of a problem with the given abstract syntax tree.

\begin{minted}{typescript}
interface Grammar {
  id: string;
  name: string;

  types: NamedLanguages;
  root?: QualifiedTypeName;
}

type NamedLanguages = Record<string, NamedTypes>;
type NamedTypes = Record<string, NodeType>;

type NodeType = NodeConcreteType | NodeOneOfType;

interface QualifiedTypeName {
  typeName: string;
  languageName: string;
}

\end{minted}

\section{Providing Blocks: The sidebar}

\begin{wrapfigure}{r}{0.3\textwidth}
  \includegraphics[width=\linewidth]{screenshots/sidebar-sql}
  \caption{BlattWerkzeug showing two sidebars with partially opened categories}
  \label{fig:sidebar-sql}
\end{wrapfigure}

On the surface the sidebar simply fulfills an elemental requirement in any block based environment: This is the source of the available blocks, the place where blocks are dragged from. And while this is obviously a hard requirement, it has an important secondary as a memory aid. In text based programming options available are usually learned in advance and have to be remembered. Looking at available blocks allows the learner to pick from a set of options, possibly by recalling their function once she or he sees them.

As Blatt-Werkzeug is distinctly aiming to work with real world programming languages, the blocks are often resembling syntactic constructs like \texttt{if}, \texttt{for}, \texttt{SELECT}, \texttt{<h1></h1>}, ... These identifiers are not as self-explanatory as in for example Scratch and it's stage metaphor with things like \texttt{Move}, \texttt{Say}, \texttt{Play Sound}, ... But this is not an inherent shortcoming of the approach: Most of these easier to grasp operations are simply function calls under the hood.. The \nameref{sec:trucklino} runtime demonstrates a wide range of \enquote{natural} blocks to move a truck forward, set turn signals or to sense traffic lights.

In BlattWerkzeug blocks in the sidebar are part of a three level hierarchy:

\begin{itemize}
\item The \textbf{top level sidebar} may appear multiple times and have a caption. \Cref{fig:sidebar-sql} shows examples named \enquote{Datenbank \texttt{default}} and \enquote{SQL}.
\item Each sidebar defines collapsible \textbf{categories} which are also named. \Cref{fig:sidebar-sql} shows examples named \enquote{Auftritt}, \enquote{Charakter}, ... to list all tables and \enquote{Ausdrücke}, \enquote{Funktionen}, ... to group SQL blocks. In the state of the screenshot, only the category for table \enquote{Auftritt} and the category \enquote{Funktionen} are opened. Note that in the case of the tables, the category itself is also a draggable block.
\item Below the category is where \textbf{blocks} themselves are defined and also display a caption.
\end{itemize}

\Cref{fig:sidebar-sql} also gives a hint, that there must be statically and dynamically populated sidebars: The syntactic elements of SQL are known in advance and can be specified using a grammar. But the schema of the database changes at runtime and can not meaningfully be defined by a grammar.
